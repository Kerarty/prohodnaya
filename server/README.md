# Сервер матчмейкинга «Проходная» — фаза 2

Минимальный сервер асинхронных дуэлей: оба игрока играют один и тот же забег
(один сид, 90 секунд), результаты сравнивает сервер. Реалтайм-синхронизации
нет — только HTTP-поллинг состояния и один POST результата.

Реализация: **один файл `server/index.mjs`, чистый Node.js >= 18, только
встроенные модули (`http`, `crypto`, `fs`), ноль npm-зависимостей.**

## Запуск

```bash
node server/index.mjs            # порт 8787
node server/index.mjs --port 9000
```

Проверка живости: `curl http://127.0.0.1:8787/api/ping` → `{"ok":true}`.

CORS: все ответы (включая ошибки и OPTIONS preflight) содержат
`Access-Control-Allow-Origin: *` — игра может лежать на любом origin.

## Хранилище

Всё состояние — в памяти процесса. Раз в 30 секунд оно целиком (рейтинги,
матчи, очередь) best-effort сбрасывается в `server/data.json` (атомарно:
tmp + rename) и загружается оттуда при старте, если файл есть. `data.json` —
runtime-артефакт, можно удалять между запусками. Также дамп делается при
остановке процесса (SIGINT/SIGTERM). Завершённые матчи вычищаются из памяти
через час (рейтинги остаются).

## Конфигурация

Все подогнанные числа — константы в начале `server/index.mjs`, не в логике:

| Константа | Значение | Смысл |
|---|---|---|
| `DURATION_MS` | 90000 | длительность забега (`durationMs`) |
| `COUNTDOWN_MS` | 3000 | `startAt = now + 3 c` при полном составе |
| `FORFEIT_MS` | 180000 | дедлайн результата: `startAt + durationMs + 3 мин` |
| `SCORE_CAP` | 400 | потолок очков (40 заявок × 10 очков) |
| `RESULT_RATE_LIMIT_MS` | 1000 | POST result не чаще 1/с на игрока |
| `START_RATING` / `WIN_DELTA` / `LOSS_DELTA` / `DRAW_DELTA` | 1000 / +8 / −6 / 0 | Elo-lite |
| `DUMP_INTERVAL_MS` | 30000 | период дампа в `data.json` |

`seed` матча — случайный uint32 (число 0…2³²−1), одинаковый для обоих игроков.

## Жизненный цикл матча

`waiting` (меньше 2 игроков) → `countdown` (оба в комнате, `startAt` в будущем,
клиент сам отсчитывает) → `running` (`startAt` наступил, ждём результаты) →
`results` (оба результата или дедлайн, `winner` заполнен).

Рейтинг меняется **только** когда оба результата получены, либо в дедлайн
(`startAt + durationMs + 3 мин`): не приславший = техпоражение, если соперник
прислал; оба не прислали — ничья. Дедлайн проверяется лениво при каждом
запросе (sweep), поэтому результаты появятся при ближайшем поллинге.

## Эндпоинты

### GET /api/ping

```bash
curl http://127.0.0.1:8787/api/ping
```

```json
{"ok":true}
```

### POST /api/match/quick

Тело: `{"playerId":"P1","name":"Alice"}`. FIFO-очередь: если есть ждущий
игрок (не сам) — матч с ним, иначе игрок встаёт в очередь.

```bash
curl -X POST http://127.0.0.1:8787/api/match/quick \
  -H 'Content-Type: application/json' -d '{"playerId":"P1","name":"Alice"}'
```

Ожидание (игрок в очереди, поллит state по `matchId`):

```json
{"status":"waiting","matchId":"…"}
```

Матч (второй игрок, `startAt` = момент ответа + 3 с):

```json
{"status":"matched","matchId":"…","seed":1832475611,"durationMs":90000,
 "startAt":1731700000000,"opponent":{"playerId":"P1","name":"Alice"}}
```

### POST /api/match/create

Тело: `{"playerId","name"}`. Создаёт комнату с кодом (6 символов A-Z0-9 —
без визуально двусмысленных O/0/I/1, код уникален среди активных комнат).

```bash
curl -X POST http://127.0.0.1:8787/api/match/create \
  -H 'Content-Type: application/json' -d '{"playerId":"P3","name":"Carol"}'
```

```json
{"status":"created","matchId":"…","code":"RTX7KM","seed":1832475611,"durationMs":90000}
```

### POST /api/match/join

Тело: `{"code":"RTX7KM","playerId":"P4","name":"Dave"}`. Ответ — как
`matched` у quick (создатель комнаты назначается соперником). Ошибки:
`404` — код не найден, `409` — комната полна.

```bash
curl -X POST http://127.0.0.1:8787/api/match/join \
  -H 'Content-Type: application/json' -d '{"code":"RTX7KM","playerId":"P4","name":"Dave"}'
```

### GET /api/match/{matchId}?playerId=…

Поллинг состояния (рекомендация плана: раз в 2–3 с, только в лобби).

```bash
curl "http://127.0.0.1:8787/api/match/<matchId>?playerId=P1"
```

```json
{"status":"running","matchId":"…","seed":1832475611,"durationMs":90000,
 "startAt":1731700000000,"code":"RTX7KM",
 "players":[{"playerId":"P3","name":"Carol","score":0,"finished":false},
            {"playerId":"P4","name":"Dave","score":0,"finished":false}],
 "winner":null}
```

`code` присутствует только у матчей, созданных через `create`/`join`.
`score` у не-финишировавшего = 0. `winner`: playerId | `"draw"` | `null`.
Параметр `playerId` принимается, но на ответ не влияет (контракт v1 не
предусматривает персонализацию).

### POST /api/match/{matchId}/result

Тело: `{"playerId","score"}`. Один результат на игрока на матч; `score` —
целое 0…400, больше потолка — `400`. Не чаще 1 POST в секунду на игрока —
иначе `429`.

```bash
curl -X POST http://127.0.0.1:8787/api/match/<matchId>/result \
  -H 'Content-Type: application/json' -d '{"playerId":"P1","score":120}'
```

Соперник ещё не прислал (рейтинг пересчитается при его результате):

```json
{"winner":null,"players":[{"playerId":"P1","name":"Alice","score":120,"finished":true},
                          {"playerId":"P2","name":"Bob","score":0,"finished":false}],
 "rating":{"me":1000,"delta":0}}
```

Оба прислали (или дедлайн) — рейтинг применён:

```json
{"winner":"P2","players":[{"playerId":"P1","name":"Alice","score":120,"finished":true},
                          {"playerId":"P2","name":"Bob","score":200,"finished":true}],
 "rating":{"me":1008,"delta":8}}
```

### GET /api/rating?playerId=…

```bash
curl "http://127.0.0.1:8787/api/rating?playerId=P1"
```

```json
{"playerId":"P1","rating":994,"wins":0,"losses":1,"draws":0,
 "top":[{"playerId":"P2","name":"Bob","rating":1008}, …]}
```

`top` — глобальный топ-10 по рейтингу (только игравшие игроки). Неизвестный
игрок получает дефолты (1000 / 0 / 0 / 0) без записи в базу.

## Коды ошибок

| Статус | Когда |
|---|---|
| 400 | битый JSON, нет/длинные `playerId`/`name`, `code` пуст, `score` не целое 0…400 или выше 400 |
| 404 | маршрут не найден; код комнаты не найден; матч не найден; игрок не в этом матче |
| 409 | комната полна; игрок уже в активном матче (2 игрока); результат уже прислан; матч завершён; матч ещё не начался |
| 413 | тело запроса > 64 КБ |
| 429 | POST result чаще 1/с на игрока |
| 500 | внутренняя ошибка (логируется) |

## Поведение, уточнённое сверх контракта (сетевые retry-сценарии)

- **Один активный матч на игрока.** Повторный `quick` возвращает его текущий
  матч (`waiting` либо `matched`), повторный `create` — ту же комнату с тем же
  кодом, повторный `join` участником — `matched` без сброса `startAt`. Это
  делает ретраи запросов безопасными.
- Новый `create`/`join` отменяет ждущий (одиночный) матч игрока: он удаляется
  из quick-очереди / его комната закрывается. Выйти из матча «на двоих» нельзя
  до дедлайна.
- Результат в матч, который ещё не начался (`waiting`, нет соперника), — 409.
- Rate limit учитывает **все** POST-попытки (и отклонённые): после ошибки 400
  повторная попытка в течение секунды вернёт 429.

## Анти-чит v1 (границы честно)

- один результат на игрока на матч (повтор — 409);
- потолок очков 400 (40 заявок × 10 очков), выше — 400;
- rate-limit 1 результат/с на игрока;
- проверка скорости набора очков (cap «очков в секунду») и replay-валидатор
  НЕ делаются — осознанное ограничение v1 (план, «пределы честно»).

## Ограничения и допущения v1

- **Без авторизации**: `playerId` — самопровозглашённый, возможен спуфинг
  (план, п. «Авторизация», допущение v1: риск приемлем для косметических
  наград). Проверка подписи SDK и HMAC-токены раунда не реализованы.
- **В памяти + дамп в файл**: не БД; при >100 одновременных игроков по плану
  подразумевается SQLite/Postgres (стек упрощён по ТЗ задачи, см. ниже).
- Нет heartbeat/присутствия: ушедший из очереди игрок остаётся ждущим;
  ушедший из матча получит техпоражение в дедлайн.
- Никакой серверной инфраструктуры: деплой/хостинг — вне этого сервера
  (координируется отдельно, план п. «Хостинг»).

## Как клиент подключается

1. `GET /api/ping` — сервер жив? Не отвечает → играем оффлайн (деградация
   безопасна, план п. «Принцип риска»).
2. Дуэль: `POST /api/match/quick` (случайный соперник) или
   `POST /api/match/create` + обмен кодом + `POST /api/match/join`.
3. Поллинг `GET /api/match/{matchId}` раз в 2–3 с до `status:"countdown"`,
   затем старт забега по `startAt` (сид `seed` → генерация очереди заявок).
4. После забега: `POST /api/match/{matchId}/result` со своим скором.
5. Итог и дельта рейтинга — в ответе на result; общий рейтинг —
   `GET /api/rating?playerId=…`.

Контракт API (пути и поля) совпадает с ТЗ полностью; неизбежных отклонений нет.
