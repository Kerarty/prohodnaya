# Мультиплеер «Проходной» — план

Статус: черновик на утверждение · 2026-11-16 · Ответственный: сетевой программист
Суть: асинхронный мультиплеер «одинаковый сид + гонка на время + сравнение результатов» в трёх фазах.
Реалтайм-синхронизация состояния не делается ни в одной фазе.

## 1. Цели и принципы

**Почему асинхронный формат первым**

- Yandex Games SDK не даёт транспорта «клиент–клиент»: нет реалтайм-мультиплеера, комнат, репликации. Любой живой мультиплеер = свой сервер с нуля.
- Геймплей детерминирован: seed → очередь заявок (mulberry32, `src/game/rng.ts`, `src/game/generation.ts`). Один и тот же сид всем игрокам = честная гонка без обмена ни одним игровым событием.
- Латентность не влияет на геймплей: решения принимаются локально. Сетевые цели проекта — допуск рассинхрона старта ±2–3 с и доставка результата до 3 мин. Цель «отклик 150 мс» из реалтайм-неткода здесь не применима и не проектируется.
- Анти-чит проще: сервер проверяет правдоподобность результата (потолок очков считается из сида детерминированно), а не валидирует поток действий.
- Стоимость: HTTP + одна таблица БД, держится на бесплатных тарифах.

**Что НЕ делаем (все фазы):** синхронизация состояния, предикция/реконсиляция, peer-to-peer, миграция хоста, лобби с живым присутствием (до фазы 3 — только матчи на двоих).

**Принцип риска:** каждая фаза полезна сама по себе и не блокирует одиночную игру. Отключение сервера в любой момент = игра остаётся как есть.

## 2. Фаза 1 — «Блиц» (без сервера, ~16–24 ч)

Формат: одна смена дня на всех + таймер 90 с. Вариант «фиксированные 20 заявок» отклонён: таймер — естественный ограничитель темпа, фиксированная длина очереди создаёт «фарм последней заявки».

- Сид: тот же дневной сид, что у обычной смены — `dailySeed(dateKey(now))` из `src/game/save.ts` уже реализован. Вопрос: если `dateKey` локален по таймзоне, для глобального лидерборда перевести на МСК (UTC+3), чтобы у всей аудитории «день» был общий (уточнить текущее поведение `dateKey`).
- Тренировочный блиц со случайным сидом: возможен, не пишет в лидерборд (анти-фарм). Режется первым при нехватке времени.
- Скор: существующие очки смены; тай-брейк в таблице — время забега. Int32 хватает с запасом (потолок одной смены много меньше 2^31).
- Ошибки: «3 ошибки = конец» в 90-секундном забеге делают результат слишком зависимым от удачи. Рекомендация: ошибка = −5 с таймера, конец только по таймеру. Числа в конфиг (`blitz.duration=90`, `blitz.mistakePenalty=5`); финальный тюнинг — с геймдизайном.
- Прощение: окно отмены последнего решения сохраняется, таймер не останавливается.
- Rewarded-реклама: одна точка — на экране подготовки, «+15 с к таймеру» за просмотр, 1 раз за забег. НЕ даём за рекламу: подсказку решения, перегенерацию сида, множитель очков — это ломает сравнение скилла и смысл лидерборда.
- Лидерборды: две таблицы Яндекса — `blitzDay` (период day) и `blitzBest` (allTime). Периодизация day/week/month/allTime и лимит таблиц на игру — уточнить в доках.
- UX входа: кнопка «Блиц» на главном меню → экран подготовки (сид дня, таймер, правило штрафа, rewarded-кнопка) → забег → результат (скор, рекорд, место в `blitzDay`).
- Все числа блица — в конфиге, не в коде.

## 3. Фаза 2 — «Дуэль» (минимальный сервер, ~34–48 ч)

Формат: оба игрока играют ОДИН И ТОТ ЖЕ блиц-забег с одним сидом, результаты сравнивает сервер. Обмен решениями в реальном времени отсутствует.

**Жизненный цикл матча:** created → waiting (оба в комнате) → countdown (старт по `startAt`, отсчёт 3 с) → running (оба играют локально, сети нет) → results (сервер ждёт скоры до дедлайна 3 мин) → winner.

- Матчмейкинг: (а) код комнаты — 6 символов, обмен через clipboard (clipboard API в SDK — уточнить в доках); (б) случайный соперник — FIFO-очередь в БД (без подбора по рейтингу: при малом онлайне Elo-подбор бесполезен).
- Старт: сервер шлёт `startAt` (epoch ms), клиент стартует по нему. Рассинхрон старта ±2–3 с не влияет на честность — сравниваются скоры на одинаковой очереди, а не время реакции.
- Дисконнект: скор не пришёл до дедлайна → техническое поражение (если соперник прислал); оба не прислали → ничья без очков. Переигровка не нужна: матч 90 с, дешевле создать новый.
- Транспорт: **HTTP-поллинг, не WebSocket.** Обоснование: в running-фазе сети нет вообще; поллинг нужен только в waiting/countdown (GET раз в 2–3 с) и один POST результата. WS требует долгоживущих соединений, проксирования и ручного реконнекта ради фазы, где нечего передавать. Полоса: ~350 Б × 0.4 req/с ≈ 140 Б/с на игрока в лобби, 0 Б/с в забеге. Поллинг stateless — проще деплой, отладка и масштабирование. WS оставлен фазе 3.
- Сервер: Node 20 LTS + TypeScript + Fastify; БД SQLite (better-sqlite3), при >100 одновременных — Postgres. Критично: `rng.ts` + `generation.ts` вынести в shared-пакет, чтобы клиент и сервер генерировали идентичную очередь из сида (и сервер мог детерминированно считать потолок очков).
- Сид матча: сервер генерирует случайный сид на матч (не сид дня — дуэлей в сутки много).
- Авторизация: клиент получает подписанные данные игрока из SDK (метод получения и алгоритм проверки подписи на сервере — уточнить в доках). Fallback v1: идентификация по uniqueID + серверный HMAC-токен раунда; честно: без проверки подписи возможен спуфинг uniqueID — для косметических наград риск приемлем (допущение).
- Анти-чит v1 (правдоподобность, не полная валидация):
  - токен раунда: HMAC(секрет сервера, matchId + playerId + seed + expires), одноразовый, дедлайн 3 мин, дедуп nonce;
  - сервер знает идеальный скор смены (детерминированная симуляция сида) — скор выше потолка отклоняется; cap «очков в секунду» по времени забега;
  - rate-limit: 1 результат на матч, N матчей в час на игрока;
  - **пределы честно:** последовательность решений не проверяется, «идеальный бот» не отсекается. Полный replay-валидатор (клиент присылает лог решений, сервер пересимулирует) возможен благодаря детерминизму, ~8–12 ч — отложен до появления кейса с ценными призами.
- Рейтинг дуэлей: Elo-lite — старт 1000, победа +8, поражение −6, ничья 0 (в конфиге). Полноценный Elo с K-фактором для казуала избыточен.
- Хостинг:

  | Вариант | Цена | Минусы |
  |---|---|---|
  | Cloudflare Workers + D1 | ~0 ₽ | serverless, поллинг идеален; лимиты CPU/базы (уточнить) |
  | Fly.io минимальная VM | ~$3–5/мес | деплой руками; WS поддержан (пригоден для фазы 3) |
  | Render бесплатный | 0 ₽ | cold start 30–60 с ломает быстрый матчмейкинг; лечится платным тарифом |
  | VPS | 200–400 ₽/мес | полный контроль, всё вручную |

  Рекомендация: при бюджете 0 — Cloudflare Workers + D1; иначе Fly.io.

Разбивка часов: сервер (API, матчмейкинг, токены, анти-чит, деплой) 20–28; клиент (MatchAPI, UI дуэли, интеграция) 14–20.

## 4. Общий рейтинг (фаза 2–3, ~12–16 ч)

- Сезон = календарный месяц (UTC). Две независимые витрины, не смешивать: блиц-скор (лидерборд Яндекса) и дуэльный рейтинг (своя БД). Сводного «общего рейтинга» нет — два рейтинга в одной вкладке.
- Где хранить:

  | Критерий | Лидерборды Яндекса | Своя БД |
  |---|---|---|
  | Цена/сервер | бесплатно, без сервера | сервер уже есть с фазы 2 |
  | Сброс сезона | период day/week/month у SDK (уточнить), произвольно нельзя чистить | полный контроль |
  | Метаданные (W/D/L, история) | нет | да |
  | Друзья | API друзей — уточнить в доках | можно свой код друга |
  | Независимость от платформы | привязка к Яндексу | переносима |

  Решение: блиц — у Яндекса (фаза 1 вообще без сервера); дуэли и сезон — своя БД.
- Награды сезона: топ-1 — рамка «Печать месяца»; топ-10% — косметика (рамка бейджа); топ-50% — мелкая косметика. **Жетоны за сезон в фазе 2 НЕ выдаём:** жетоны лежат в облачном сейве, который пишет клиент, — их можно задублировать. Жетонные награды — только после переноса кошелька на сервер (фаза 3+, опционально).
- Выдача: серверный скрипт закрытия сезона фиксирует топ; клиент в следующем визите показывает «награда сезона» и записывает косметику в сейв (косметика не ломает экономику даже при дюпе).
- UX: новая вкладка «Рейтинг» в кабинете: сезон + таймер до конца, топ-50 глобальный, «моя позиция», под-вкладка дуэльного рейтинга. Раздел «среди друзей» отложен (зависит от API друзей — уточнить в доках).
- Клиентская часть: экраны + рендер таблиц — 12–16 ч (серверная логика сезона входит в фазу 2).

## 5. Фаза 3 (опционально) — реалтайм-наблюдение (~24–32 ч)

- Что: соперник видит решения соперника живьём во время забега. Не синхронизация состояния — поток событий `{seq, номер заявки, решение}` (~15 Б), сервер-релей пересылает без обработки. Клиент рендерит индикатор «соперник 12/20» и вспышки решений.
- Транспорт: WebSocket. Порядок гарантирован (TCP), буфер 100 мс на burst. Реконнект не влияет на исход: результат всё равно отправляется POST-ом. Нагрузка: 1 соединение на игрока на 90–120 с; 200 одновременных коннектов — тривиально для одной VM (~30 Б/с на игрока).
- Почему последним: (а) новый транспорт и новая категория отказов в самый напряжённый момент игры; (б) долгоживущие соединения; (в) ценность зрелищная, а не механическая — удержание даёт фаза 2, не стрим решений; (г) нужен платный хостинг без cold start. Делать только при подтверждённом retention фаз 1–2.

## 6. Клиентская интеграция

- **PlatformAPI** (`src/platform/types.ts`) почти не меняется: имена лидербордов в конфиг, метод clipboard (уточнить в доках) для кода комнаты. Изоляция SDK сохраняется.
- **MatchAPI** — новый интерфейс над PlatformAPI; в фазе 1 реализуется локальной заглушкой (без сети), в фазе 2 — HTTP-клиентом:

```ts
interface MatchAPI {
  // фаза 1 (локально)
  startBlitz(): BlitzSession;                  // сид дня + таймер из конфига
  submitBlitzScore(score): Promise<BoardResult>;
  // фаза 2 (HTTP)
  createRoom(): Promise<{ code, matchId }>;
  joinRoom(code): Promise<MatchInfo>;
  quickMatch(): Promise<MatchInfo>;
  reportReady(matchId): Promise<{ startAt, seed, token }>;
  reportResult(matchId, token, score): Promise<MatchOutcome>;
  pollMatch(matchId): Promise<MatchState>;     // раз в 2–3 с, только лобби
  // фаза 2–3 (рейтинг)
  getSeasonRanking(scope): Promise<RankingPage>;
  claimSeasonReward(seasonId): Promise<Reward>;
}
```

- **Сейв** (`src/game/save.ts`): v1 → v2 аддитивно — `mp: { blitzBest, blitzRuns, duelWins, duelLosses, duelDraws, duelRating, seasonSeen, cosmetics }`. `normalizeSave` уже есть: отсутствие поля = дефолты, схема v1 не ломается, облачный сейв 200 КБ не переполняется.
- **Меню/кабинет:** кнопка «Блиц» на главном меню (фаза 1); вкладки «Дуэль» и «Рейтинг» в кабинете (фаза 2+).

## 7. Риски и отказ от объёма

- **Модерация Яндекса (главный внешний риск):** внешние HTTPS-запросы к своему бэкенду разрешены, но правила и регистрацию домена — уточнить в доках и подать ДО разработки фазы 2. Деградация безопасна: без сервера игра полностью работоспособна (блиц ничего не требует).
- **Читерство:** v1 — доверенный клиент с потолками правдоподобности; спуфинг uniqueID без серверной проверки подписи — осознанное допущение. Полный валидатор отложен. Для косметических наград риск приемлем.
- **Дюп наград через облачный сейв:** снят выбором «сезонные награды = только косметика».
- **Нагрузка/стоимость:** 0 игроков — 0 ₽ (serverless) или спящая VM; всплеск 100 CCU → ~35 rps поллинга — тривиально для одного инстанса; фаза 3 — 200 WS-коннектов, тоже тривиально. Реальный риск — не нагрузка, а cold start бесплатных тиров и лимиты serverless.
- **Что режем первым (порядок):** 1) тренировочный блиц со случайным сидом; 2) «среди друзей»; 3) жетонные награды сезона; 4) replay-валидатор; 5) фаза 3 целиком.
- **Kill-критерий:** если через 2 недели после релиза блица его не играет <15% DAU — фазы 2–3 не делать (мультиплеер не окупает 40+ ч).

## 8. Дорожная карта

| Фаза | Объём | Часы (соло) | Зависимости | Критерий готовности |
|---|---|---|---|---|
| 1. Блиц | таймер, сид дня (МСК), штраф ошибок, rewarded-точка, 2 лидерборда, UX | 16–24 | — | забег от кнопки до места в blitzDay без ручных вмешательств; числа в конфиге |
| 2. Дуэль | сервер Node+SQLite, матчмейкинг (код + FIFO), HMAC-токены, анти-чит потолками, Elo-lite, MatchAPI + UI | 34–48 | фаза 1; домен одобрен модерацией (уточнить) | два устройства: код комнаты → матч → победитель и очки; скор выше потолка отклоняется |
| 2.5 Рейтинг | скрипт закрытия сезона, вкладка «Рейтинг», косметика, выдача | 12–16 | фаза 2 | закрытие месяца скриптом: топ зафиксирован, награда выдана, сезон обнулён |
| 3. Реалтайм | WS-релей, поток событий, индикатор соперника | 24–32 | фаза 2.5 + retention-метрики | живой индикатор «соперник N/20» при стабильном соединении |

Итого до конца фазы 2.5: ~62–88 ч ≈ 2–3 месяца при 10 ч/нед.
